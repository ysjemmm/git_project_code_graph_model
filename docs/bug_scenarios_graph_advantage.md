# 代码图谱优势场景：典型 Bug 案例

本文档分两类：**跨仓库 Bug** 与 **单仓库 Bug**。这些场景下，若仅靠「拉仓库 + grep/搜索」，排查成本高、易漏；而用图数据库做依赖/调用/继承分析，可显著缩短定位时间、提高 AI 修复建议的准确性。

---

## 一、跨仓库 Bug（多仓库 + 二方包 + 多分支）

### Bug 1：二方包升级导致的方法签名变更

**Bug 描述**：某二方包 `common-utils@2.1.0` 升级到 `2.2.0`，内部方法 `parse(String)` 改为 `parse(String, Charset)`，旧签名被标记 `@Deprecated`。线上多个业务仓库都依赖该二方包，部分仍在使用旧签名，导致编译失败或运行时 `NoSuchMethodError`。

**仅拉仓库的痛点**：
- 需要逐个仓库 `grep "common-utils"`、`grep "parse("`，再人工判断是否调用的是该二方包的方法
- 二方包源码通常不在业务仓库内，无法直接搜索「谁在调这个方法」
- 多仓库 × 多分支，人工排查极易遗漏

**代码图谱的优势**：
- `JavaObject(from_type='ExternalDefinition')` 已建模二方包中的类；`LIB_LINK` 可关联到业务仓库中的实现
- `MATCH (caller)-[:CALLS]->(callee)` 精确找到「谁在调用 `parse`」
- 按 `project_key` 过滤，一次查询即可列出「所有仓库中调用该二方包 `parse` 的调用点」
- 直接给 AI「受影响的方法列表 + 调用链子图」，无需在成堆文件中盲目搜索

---

### Bug 2：废弃 API 的全局替换（多仓库、多调用点）

**Bug 描述**：某内部工具类 `DateUtils.format(Date)` 被标记为废弃，推荐使用 `DateUtils.format(Date, ZoneId)`。需要找出所有调用点并给出替换建议，涉及 10+ 仓库、数百个文件。

**仅拉仓库的痛点**：
- `grep "DateUtils.format"` 会命中大量无关结果（注释、字符串、类似方法名）
- 无法区分「调用的是单参数还是多参数重载」
- 多仓库要分别搜，汇总和去重都靠人工

**代码图谱的优势**：
- `(caller_method)-[:CALLS]->(DateUtils.format)` 精确到「方法级调用」
- 按 `project_key` / `belong_project` 聚合，一次查询得到「所有仓库的调用点清单」
- 直接给 AI「调用点列表 + 上下文代码路径」，生成替换补丁时无需再搜索

---

### Bug 3：二方包与业务代码的「同名不同实现」混淆

**Bug 描述**：业务仓库和某二方包都定义了 `com.example.Conf`，但实现不同。某处代码误用了二方包的 `Conf` 而非业务自己的，导致配置读取错误。需要找出「所有引用二方包 `Conf` 的地方」，并判断是否应改为业务 `Conf`。

**仅拉仓库的痛点**：
- `grep "Conf"` 会命中大量无关类
- 无法区分「来自二方包」还是「来自业务代码」，需结合 import 和 classpath 人工判断
- 多仓库、多模块下，classpath 复杂，人工极易出错

**代码图谱的优势**：
- `InnerDefinition` vs `ExternalDefinition` 明确标记来源
- `qualified_name + belong_project` 可精确区分「业务 Conf」与「二方包 Conf」
- 可查出「谁在用二方包的 Conf」，`LIB_LINK` 可辅助判断「是否应使用内部实现」

---

## 二、单仓库 Bug（单一仓库内）

### Bug 4：接口/抽象类方法签名变更（继承链影响面）

**Bug 描述**：某基础接口 `BaseService` 新增了一个抽象方法 `validate()`，所有实现类必须实现。漏实现会导致编译失败或 `AbstractMethodError`。需要找出「所有实现 `BaseService` 但未实现 `validate()` 的类」。

**仅拉仓库的痛点**：
- `grep "implements BaseService"` 能找到直接实现类，但**多层继承**（A extends B implements BaseService）会漏
- 需要递归分析继承树，人工容易漏掉间接实现类

**代码图谱的优势**：
- `(Child)-[:EXTENDS]->(Parent)`、`(Impl)-[:IMPLEMENTS]->(Interface)` 已建模
- 一次 Cypher 即可查出「所有直接或间接实现 `BaseService` 的类」
- `(Class)-[:MEMBER_OF]->(Method)` 可判断每个实现类是否包含 `validate()` 方法
- 图查询可直接输出「需补 `validate()` 的类列表」，无需人工递归

---

### Bug 5：循环依赖 / 潜在死锁（调用链环路）

**Bug 描述**：某次上线后出现偶发死锁，怀疑是 A→B→C→A 的调用链在特定并发下形成环路。需要快速找出「所有可能存在循环调用的链路」。

**仅拉仓库的痛点**：
- 无结构化调用关系，只能靠静态分析工具或人工画调用图
- 跨类、跨包的调用链难以完整还原

**代码图谱的优势**：
- `MATCH path = (a)-[:CALLS*]->(a)` 可查出「调用链最终回到自己的方法」
- `[:CALLS*2..10]` 可控制搜索深度，避免爆炸
- 图数据库天然支持「路径可视化」，便于和 AI 一起分析死锁成因

---

### Bug 6：字段/常量变更的级联影响

**Bug 描述**：某常量 `MAX_RETRY = 3` 被改为 `5`，或某字段 `config.timeout` 的语义变更。需要找出「所有读取该字段/常量的地方」，评估改动影响。

**仅拉仓库的痛点**：
- `grep "MAX_RETRY"` 或 `grep "timeout"` 噪声极大
- 无法区分「同一类内引用」与「跨类访问」
- 字段访问关系通常需要数据流分析，纯文本搜索难以胜任

**代码图谱的优势**：
- `(Method)-[:ACCESSES]->(Field)` 已建模字段访问
- 一次查询即可得到「所有访问该字段/常量的方法」，再结合 CALLS 可扩展为「调用链影响面」
- 影响面可量化，避免改一处引发隐性故障

---

## 总结

| 类型     | 典型 Bug                         | 图谱核心优势                           |
|----------|----------------------------------|----------------------------------------|
| 跨仓库   | 二方包升级、废弃 API 替换、同名类混淆 | 一张图、按 project_key 过滤、ExternalDefinition + LIB_LINK |
| 单仓库   | 接口变更漏实现、循环调用、字段影响面   | EXTENDS/IMPLEMENTS、CALLS 环路、ACCESSES |

**一句话**：但凡涉及「谁依赖谁、谁调谁、影响面有多大」，图谱都能把「搜索 + 推理」变成「查询」，优势巨大。
